Software & Software Engineering

Software Engineering (MAI-104) introduces the systematic process of building software — from requirements through design, coding, testing, deployment, and maintenance. This section lays the foundation: what software is, what software engineering means, and why disciplined engineering matters.

What is Software?

Software is a collection of instructions (programs) and data used to operate computer systems, hardware, or machines and perform specific tasks — such as calculating, editing, gaming, or browsing.

📘
Hierarchy: Code → Program → Software. Code is the raw text written by a developer; a program is a set of instructions; software = programs + documentation + data.

What is Software Engineering?

Software Engineering is the application of structured engineering rules to build software — treating development as a planned, disciplined, step-by-step practice rather than random coding. It ensures software is built correctly, efficiently, and at scale.

Goals of Good Software

  • Reliable — works correctly and consistently without crashing
  • Efficient — uses memory and processing power wisely
  • Maintainable — easy for other programmers to fix, modify and update
  • Affordable — completed within agreed budget and time

Software Development Life Cycle (SDLC)

The Software Development Life Cycle (SDLC) is the step-by-step journey of turning a raw idea into a finished, working software product. It is the action plan every development team follows, from start to finish.

Six Phases

1. Requirements → 2. Design → 3. Coding → 4. Testing → 5. Deployment → 6. Maintenance
💡
Universal lifecycle: The same cycle applies to all software — web apps, mobile apps, AI systems, machine-learning models, and deep-learning pipelines. Each still requires requirements, design, implementation, testing, deployment, and maintenance.

1.1   Software Engineering Paradigms

A paradigm is a chosen strategy or model that defines how the SDLC is structured and executed. It shapes how a team plans, builds, and delivers software.

ModelNatureBest ForKey Risk
Waterfall Linear, sequential Fixed, well-understood requirements No working software until the end
Spiral Iterative + risk-driven Large, mission-critical projects Expensive; needs risk experts
Prototype Iterative via feedback Unclear or vague requirements Prototype mistaken for final product
🎯
Exam tip: Choose Waterfall when requirements are stable, Spiral when risk is high, and Prototype when requirements are unclear.

1.2   Waterfall Model

The Waterfall model is a linear, sequential approach where each phase must be completed before the next one begins. It is the oldest and simplest SDLC model.

1 Requirements Analysis
↓
2 System Design
↓
3 Implementation (Coding)
↓
4 Integration & Testing
↓
5 Deployment
↓
6 Maintenance

✔ When to Use

  • Short projects with fixed budgets
  • Stable, well-understood requirements
  • Zero ambiguity (government contracts)
  • Hardware-integrated software

✘ Limitations

  • No working software until the very end
  • Mistakes in Step 1 are costly later
  • Cannot handle changing requirements
  • Testing happens very late
📌
Note: Waterfall is documentation-heavy — every phase produces a deliverable (SRS, design document, test report) before moving to the next.
🎯
Exam tip: Waterfall is the classic baseline — every other model in this unit is compared against it.

1.3   Spiral Model

The Spiral model is a risk-driven, iterative meta-model. Development proceeds in continuous loops — each loop is a mini-cycle, and the system grows with every turn. Like rolling a snowball down a hill, stopping often to check for rocks (risks).

The Four Quadrants (every loop)

  1. Planning — define goals and alternative solutions
  2. Risk Analysis — identify risks, build prototypes to test feasibility
  3. Engineering — build and test the product for this loop
  4. Evaluation — customer reviews progress; next loop is planned

✔ When to Use

  • Massive, mission-critical projects
  • High-risk domains (banking, aerospace)
  • Complex and uncertain requirements

✘ Limitations

  • Very expensive and time-consuming
  • Needs experts who can predict risks
  • Not suitable for small projects
🎯
Exam tip: Spiral is the only SDLC model where risk analysis is a formal phase — not an afterthought.

1.4   Prototype Model

An early, incomplete version of the software is built, shown to users, and refined based on their feedback — like making a cheap clay model of a statue before carving the real marble.

Two Types

Throwaway Prototype

Built only to test an idea or clarify requirements, then discarded before the final product is developed.

Evolutionary Prototype

Built as a foundation and gradually upgraded into the final product through successive refinements.

Process

Gather Requirements → Build Prototype → User Review → Refine → Final Product

✔ Advantages

  • Clarifies vague requirements early
  • Strong user involvement
  • Reduces risk of building the wrong thing

✘ Limitations

  • Users may mistake prototype for final
  • Can cause scope creep
  • Extra cost and time
🎯
Exam tip: Throwaway prototypes clarify requirements and are thrown away; evolutionary prototypes become the final product.

1.5   Software Requirements

A requirement is a condition or capability the system must have to satisfy a contract, standard, or user need. Requirements engineering is the foundation of software development — getting it wrong is the most expensive mistake in the SDLC.

Types of Requirements

Functional Requirements

What the system must do — features, calculations, and behaviour.

e.g. "A user can log in with email and password."

Non-Functional Requirements

How the system should behave — quality attributes.

e.g. "The page must load in under 2 seconds."

Requirements Engineering Process

Elicitation → Analysis → Documentation → Review

Requirement Analysis Tools

  • DFD — maps how data enters, moves through, and exits the system
  • CFD / Flowchart — step-by-step logic and decisions
  • ERD — entities, attributes and relationships for the database
  • Data Dictionary — glossary of exact data formats and rules
  • Decision Tables — matrices for complex logical rules
🎯
Exam tip: Functional = what it does (verbs and features); Non-functional = how well it does it (performance, security, usability).

1.6   Requirements Elicitation Techniques

Elicitation is the active process of gathering needs, expectations, and constraints from stakeholders.

TechniqueDescription
InterviewsOne-on-one discussions — open-ended (exploratory) or structured (fixed agenda)
QuestionnairesSurveys to gather data from a large user base quickly
ObservationsShadowing users to uncover unspoken pain points
BrainstormingGroup sessions for high-volume idea generation; criticism suspended
Use Case DevelopmentNarrative scenarios showing how users interact with the system
Delphi TechniqueAnonymous iterative expert voting until consensus — avoids groupthink
FASTFacilitated workshops where developers + clients jointly define requirements
QFDQuality Function Deployment — prioritize features by the "voice of the customer"
🎯
Exam tip: Interviews and questionnaires are direct methods; observation and brainstorming are indirect. Delphi and FAST are group techniques.

1.7   SRS Document (IEEE 830)

The Software Requirement Specification (SRS) is the definitive output of the requirements phase. It is both a blueprint for developers and a formal contract with the client.

Structure — IEEE 830

1. Introduction Purpose · Scope · Definitions & Acronyms · References · Overview
2. Overall Description Product Perspective · Functions · User Characteristics · Constraints · Assumptions
3. Specific Requirements Interfaces · Functional · Performance · Design Constraints · Database · System Attributes
4. Change Management Process Formal procedure for handling future requirement changes
5. Supporting Information Appendices · Diagrams · Flowcharts · Index

Characteristics of a Good SRS

  • Complete — covers all functional and non-functional requirements
  • Consistent — no contradictions within the document
  • Unambiguous — clear, precise and understandable
  • Verifiable — every requirement can be tested
  • Traceable — linked to source and design
  • Modifiable — structured so it is easy to update
✅
Best practice: The SRS should be reviewed by an independent third-party expert before design begins — this prevents expensive errors from cascading downstream.
🎯
Exam tip: Remember the six traits: Complete, Consistent, Unambiguous, Verifiable, Traceable, Modifiable.

1.8   Requirements Change Management

Requirements will change. Change management is the formal procedure for handling, approving, and documenting changes to requirements once the project has started.

The Flow

  1. Change Request — a stakeholder submits a formal request
  2. Impact Analysis — assess the effect on schedule, cost, design and testing
  3. Approval / Rejection — the Change Control Board (CCB) decides
  4. Implementation — update SRS, design, code and tests
  5. Documentation & Traceability — log the change in version history
⚠️
Why it matters: Unmanaged changes cause scope creep — the project keeps expanding and never finishes.
🎯
Exam tip: Change Management always starts with a formal request and ends with a logged, traceable record — never with an ad-hoc edit.

1.9   Project Management

Project management ensures software is delivered on time, within budget, and to the required quality — through metrics, scheduling, and risk management.

Software Metrics

TypeWhat It MeasuresExamples
ProductThe software itselfLOC, complexity, defect density
ProcessThe development methodBug-fix time, review efficiency
ProjectExecution of the projectBudget, time, staffing

Common Metrics

  • LOC — lines of code
  • Cyclomatic Complexity — number of decision paths
  • Defect Density — bugs per 1,000 lines of code
  • Code Coverage — % of code exercised by tests
  • MTTF — mean time to failure
  • MTTR — mean time to repair

Risk Management

  • Identify threats early
  • Assess probability and impact
  • Plan mitigation

Scheduling Tools

  • Gantt Chart — visual timeline
  • PERT — probabilistic time estimation
  • CPM — critical path method
📏
Golden rule: You cannot manage what you do not measure. Metrics act as an early-warning system for risks.
🎯
Exam tip: Product = code · Process = team · Project = plan. Each metric type answers a different question.
